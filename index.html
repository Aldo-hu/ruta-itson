Proyecto de unidad: analizamos y comunicamos las 7 fases del ciclo de vida del desarrollo de software, usando como caso de estudio un mapa interactivo para estudiantes de nuevo ingreso del campus ITSON Guaymas.

Introducción: el SDLC y el reto de construir software

¿Qué pasaría si intentáramos construir un edificio sin planos, sin arquitectos y sin estudiar el terreno? Seguramente sería un desastre. Al crear programas ocurre lo mismo. Por ejemplo, Zitelia desarrolló un mapa turístico interactivo específico para una asociación que ofrece rutas turísticas, donde los usuarios navegan de manera intuitiva por las rutas y puntos destacados. Para crear sistemas estables, los profesionales no escriben código sin más: siguen un método ordenado.

Según IBM, este método es el Ciclo de Vida del Desarrollo de Software (SDLC), un proceso estructurado que divide la creación de un sistema en distintas fases conectadas, cada una con sus propios entregables que guían a la siguiente, para obtener un producto de calidad. IBM identifica siete fases clave; para este trabajo las nombramos así: Planificación, Análisis, Diseño, Desarrollo, Pruebas, Despliegue, y Mantenimiento.

Para entender cómo funciona, aplicaremos el SDLC a un problema cotidiano: un estudiante de nuevo ingreso que se pierde buscando su salón el primer día de clases. Será un caso hipotético: mostraremos cómo se llevaría a cabo siguiendo el SDLC, tomando como base el proyecto de Zitelia para crear un mapa interactivo del campus. A lo largo del proceso, cada fase genera un entregable (según IBM, lo que se produce en esa etapa y sirve de base para la siguiente: un documento, un diseño o una parte del software). Veremos cómo una simple idea evoluciona hasta convertirse en un producto real.

Cierre: el producto en acción y respaldo técnico

Lo que vemos en el video cumple, en este caso ilustrativo, la meta de 3 segundos fijada en la Fase 2 y comprobada en la Fase 5. Empezamos con una idea: ayudar a un estudiante a no perderse en sus primeros días de clases. En la planificación esa idea se volvió un cronograma y un alcance; en el análisis, en requisitos con metas medibles; en el diseño, en planos y maquetas; en el desarrollo, en código y un mapa funcional; en las pruebas, en una versión corregida y evaluada; en el despliegue, en un producto en funcionamiento en vivo; y en el mantenimiento, en nuevas versiones que lo mantienen útil. La misma idea creció fase por fase. Gracias a la arquitectura modular de la Fase 3, en el futuro podremos actualizar los colores o el diseño reduciendo el riesgo de borrar los caminos trazados. Este caso ilustrativo demuestra que el Ciclo de Vida del Desarrollo de Software nos brinda una metodología ordenada para transformar un problema cotidiano en una solución confiable con software.

Glosario

Alcance
La definición exacta de qué incluye el proyecto actual y qué se deja para versiones futuras.
Arquitectura Modular
Diseñar el sistema en piezas separadas para que un cambio visual no afecte los datos guardados.
Caso de Uso
Una descripción de cómo un usuario interactúa con el sistema para lograr un objetivo.
Control de Versiones
Sistema que guarda el historial de todos los cambios del proyecto.
Dependencias
Tareas que no pueden comenzar hasta que otra tarea previa haya sido terminada.
Despliegue y La Nube
Despliegue es llevar el código a un entorno público; la nube son los servidores en internet que lo alojan.
Entregable
Lo que produce cada fase (un documento, un diseño o una parte del software) y sirve de base para la siguiente.
Frontend, Backend y Base de Datos
Frontend es lo que el usuario ve y toca; Backend es la lógica interna que hace los cálculos; Base de Datos es el archivo central donde se guarda toda la información.
IDE y Librería
Un IDE es el programa donde se escribe el código; una librería es un conjunto de código ya hecho que resuelve tareas comunes.
Lanzamiento Canary (Gradual)
Estrategia de liberar una actualización solo a una pequeña parte de los usuarios para comprobar su estabilidad.
Norma ISO 25010
Estándar internacional que clasifica las características necesarias para evaluar la calidad de un software.
Pruebas de Integración y de Estrés
Las de integración aseguran que las piezas del código funcionen unidas; las de estrés evalúan el rendimiento con muchos usuarios simultáneos.
Requisito Funcional vs. No Funcional
Lo funcional es qué hace el sistema; lo no funcional es cómo lo hace (velocidad, accesibilidad, presentación).
SDLC
Metodología que divide la creación de software en pasos ordenados para entregar un producto de calidad.
Tipos de Mantenimiento
Correctivo (arreglar fallos), Adaptativo (ajustarse a tecnologías nuevas), Preventivo (evitar problemas futuros) y Perfectivo (añadir funciones nuevas).
UX / UI
UX es qué tan fácil es navegar; UI es el aspecto visual (colores, distribución, botones).
Verificar vs. Validar
Verificar es comprobar que el sistema cumple las reglas escritas; Validar es confirmar que realmente le sirve al usuario final.
